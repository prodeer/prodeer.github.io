前段时间我一直在研究 DeerFlow，同时也在思考：这套带 Agent Runtime、Sandbox、Skill、MCP、长期记忆和定时任务的框架，除了做通用聊天，还能做成什么真正可用的产品？

最后我做出了一个“多页面网站原型生成 Agent”：用户只输入一个产品名称，它会研究业务、规划页面、生成 HTML/CSS/JavaScript、实现交互、逐状态截图、自动验收、失败后续跑，最后交付一个 ZIP。

在 DeerFlow 的代码和配置里，我把这个专用 Agent 命名为 `website-prototyper`，后文也会沿用这个名字。

这篇文章主要是整理那条逐渐清晰的决策轨迹：一个看起来只是“帮我生成网页”的需求，为什么最后演变成了 **Agent + Skill + Manifest + Playwright + Gateway 控制面**。

这篇文章也会依次回答四个问题：怎么让 Agent 知道该做什么（Manifest）、怎么让它自己跑完（无人值守）、怎么让我知道进度（飞书推送）、以及现在的架构长什么样。

<!--more-->

## 1. 一开始，我甚至没决定要做什么

调研过程中，我列过研究平台、报告生产、数据分析、知识助理、研发 Agent 等几个方向。但这些方向都太“平台化”，离我真正想解决的问题还有些远。

恰好身边有人在做这样一套流程：先让 AI 根据系统名称生成网站原型，再依据原型开发前后端，最后手工截图交付。整个过程步骤多、耗时长，还有大量重复操作。于是我萌生了把它做成 Agent 的想法。

就这样，我决定先做一个网站原型生成的 Agent，顺便熟悉一下 DeerFlow。

## 2. 从“一个页面”到“一套网站”

如果需求只是生成一个 `index.html`，现有模型加文件工具已经能做到。但我真正想要的是“一套网站”：

> 网页原型生成助手不能只生成一个 index.html。比如给一个名字是“压板状态在线监视系统”，要生成符合这个名字的一套网站，包含多个增删改查页面。每个页面都要自动截图；点击按钮后出现的弹框，也算一个独立业务状态，也要截图。

这个需求把任务从“代码生成”推向了“产品原型生成与验收”。它至少引出了四个新问题：

1. 一个产品应该包含哪些页面？
2. 一个页面有哪些需要交付的业务状态？
3. Agent 怎么知道自己有没有漏掉页面和状态？
4. 我怎么判断它真的完成了，而不是只在回答里说“已完成”？

仅靠 Prompt 无法可靠回答这些问题。模型可以临时列一个清单，但只要生成过程变长，清单、代码和最终截图就可能逐渐偏离。

于是整个 Agent 最重要的中间产物诞生了：`site-manifest.json`。

## 3. Manifest 不是说明文档，而是可执行规格

Manifest 会在写页面之前生成，记录网站名称、视觉方向、页面路径、导航分组，以及每个业务状态的操作步骤和结果断言。

一个简化后的状态大致如下：

```json
{
  "id": "alarm-detail",
  "title": "告警详情弹框",
  "actions": [
    {
      "type": "click",
      "selector": "[data-action='open-alarm']"
    }
  ],
  "assert": "[role='dialog'][data-state='open']"
}
```

Playwright 不需要理解“告警详情”是什么意思。它只需要从一个全新的页面环境开始，找到按钮、执行点击、等待断言元素出现，然后截图。

这让 Manifest 同时承担了四种角色：

- **信息架构清单**：有哪些页面；
- **交互测试清单**：每个状态如何触发；
- **截图任务清单**：最终应该有多少张图；
- **完成度基线**：还缺哪些页面或状态。

从这一步开始，Agent 的完成标准第一次变得可以计算：

```text
预期截图数 = 页面默认状态数 + Manifest 中声明的业务状态数
```

**通用原则**：任何需要 Agent 自主完成的复杂任务，都应该有一个中间产物充当“可执行规格”。这个产物既驱动执行，也驱动验收。没有这样的中间产物，就很难判断 Agent 是否真的完成了任务。

当然，它也带来一个新的边界：**Manifest 没有声明的状态，自动验收就看不见。** 所以 Manifest 的完整性，实际上决定了整个系统测试覆盖率的上限。

## 4. 无人值守：摆脱“回复继续”的三层兜底

第一次运行时，我输入一个题目，让它开干，就去忙别的事了。过了一段时间回来查看，发现它正在等待我回复“继续”。我想：

> 能不能去掉让我回复“继续”的功能，让它自己执行就行了？

如果只改 Prompt，这个问题仍然可能在递归上限、模型空响应或运行异常时重新出现。所以最终处理了三层：

- Agent 不允许调用澄清工具，自动采用合理默认值；
- Gateway 强制 `non_interactive=true`；
- 未通过最终验收时，沿用原目录和进度自动续跑，最多 5 次。

续跑不会重新设计网站，而是读取现有 Manifest、页面、CSS 和截图进度，继续补齐或修复。用户主动点击“停止”仍然是最终操作，不会被系统擅自拉起。

后来又遇到一次典型的模型参数问题：模型把单次输出额度几乎全部消耗在 reasoning 内容上，工具执行结束后没有留下最终可见回答。于是这个专用 Agent 被服务端强制设为非 Thinking 模式，并移除了不兼容的 `reasoning_effort` 参数。

这不是在说“Agent 不需要思考”，而是生产型工作流不应该把大量额度用于展示过程旁白。这里更需要的是工具调用、文件产出、验证修复和最终交付。

## 5. 进度可视化：用飞书推送替代干等

网站生成可能持续几十分钟，一直守着页面并不现实。于是下一个问题自然出现了：能不能增加消息推送？

> 一次规划多少个页面是可知的吗？能不能做到完成进度多少就飞书推送一次，比如达到 30%、70%、100% 时推送进度？

正好 DeerFlow 支持连接飞书，而 `site-manifest.json` 一旦生成，主要页面数、业务状态数以及最终应截图数量就是确定的。因此我把进度定义成可验证的里程碑，最终进度完全由文件事实驱动：

| 进度 | 可验证条件 | 含义 |
|---|---|---|
| 30% | 发现完整的 `site-manifest.json` | 页面和状态规划完成 |
| 70% | 发现 `screenshots/progress.json` | 已进入 Playwright 验收 |
| 100% | 报告全部通过且 ZIP 有效 | 真正完成并可交付 |

飞书 100% 完成通知中还会显示总耗时。验收失败时则发送单独的失败通知，带上通过数、失败项、预览 ZIP 状态和自动修复进度，但不会误报 100%。

## 6. 热重载事故，让我看到了单机架构的边界

开发过程中还有一次很现实的事故：Gateway 触发热重载后进入 `Shutting down / Waiting for background tasks to complete`，而网站生成任务仍在后台执行。结果不只是当前对话卡住，而是所有依赖 Gateway API 的页面都一直显示“加载中”。

> 怎么做成等待任务的同时，不影响其他页面的交互？

第一步是把 `make dev` 改成稳定单机模式：Gateway 使用单进程、前端使用预构建产物，两边默认都不开热重载，需要开发时再显式开启。这解决了本地开发中的直接诱因，却没有改变一个事实：长任务仍然和 Gateway 共享进程生命周期。

这次事故暴露的并不只是热重载配置问题，而是控制面和执行面耦合在了一起：Gateway 既要响应页面和 API，又要承载可能运行几十分钟的 Agent、Sandbox 和 Playwright。只要执行侧进入关闭等待、阻塞或崩溃，交互侧就会一起受到影响。

**教训**：长任务 Agent 的控制面与执行面必须分离。只要执行任务可能超过 30 秒，就不应该和 HTTP 响应循环共享进程生命周期。

所以在稳定单机模式之后，我继续实现了 Gateway/Worker 分离。它不再只是设想，而是当前网站原型 Agent 的实际运行方式。

## 7. 现在的 Agent 是什么样的

当前的“多页面网站原型生成”仍然是 DeerFlow Lead Agent 运行时上的一个内置专用 Agent。变化的不是 Agent 定义，而是执行位置：普通 Agent 仍可在 Gateway 内执行，`website-prototyper` 则被路由到独立 Worker。

输入一个名字，交付一个包含源码和截图的 `site.zip`。

![website-prototyper Gateway / Worker 四层架构](/images/ai/deer-flow-website-prototyper-architecture.svg)

核心分为四层：

### 7.1 Agent 定义层

`website-prototyper` 仍然由原来的 Agent Factory 创建，包含自己的提示词、网站生成 Skill、工具白名单、中间件和 Playwright 能力。它不需要知道自己运行在 Gateway 还是 Worker，因此没有出现第二套 Agent Runtime。

### 7.2 任务调度层

Gateway 负责：

- 用户鉴权和线程权限检查
- 判断 Agent 名称
- 创建持久化 Run 记录
- 保存经过脱敏的 Worker 执行参数
- 尝试通过 Redis 唤醒 Worker
- 向前端提供运行状态、SSE、停止接口

当前路由规则是：

```text
website-prototyper -> Agent Worker
其他 Agent          -> Gateway 内执行
```

以后只需把 Agent 名称加入 `agent_worker.agents`，就可以逐步迁移到 Worker，不需要重新实现一套运行框架。

### 7.3 Worker 执行层

Worker 优先从 Redis 获取唤醒通知，然后在 SQL 中原子领取任务并设置租约。真正执行时仍然调用 DeerFlow 统一的 `run_agent()`：

```text
领取 Run
  -> 恢复用户与线程上下文
  -> resolve_agent_factory()
  -> 创建 website-prototyper
  -> 执行 LangGraph
  -> 写 checkpoint、artifact 和状态
  -> 发布 SSE 事件
```

Redis 通知丢失或重复都不会改变任务语义：Worker 还会主动扫描 SQL，并且只有成功获得租约的 Worker 才能执行。因此 SQL 才是可靠任务源，Redis 只是用于缩短任务发现时间。

### 7.4 状态与恢复层

不同数据分别承担不同职责：

| 数据 | 作用 |
|---|---|
| SQL `runs` | 任务状态、Worker 所有权、租约、停止请求和领取次数 |
| Redis 唤醒队列 | 快速通知 Worker 有新任务，不承担持久化真源职责 |
| Redis StreamBridge | 把 Worker 产生的事件传回 Gateway，继续提供跨进程 SSE |
| Checkpoint | Worker 崩溃后恢复 LangGraph 执行状态 |
| 共享存储 | 保存网站源码、截图、报告和 `site.zip` |
| SQL Notification Outbox | 持久化飞书通知，由 Gateway 发送并在失败后重试 |

这里要区分两种恢复：网站验收失败时，业务层会创建隐藏的续跑 Run，读取原目录和失败报告继续修复，最多 5 次；Worker 进程崩溃时，基础设施层会在租约过期后重领同一个 Run，并从 Checkpoint 恢复，不会重新播放原始用户输入。

停止任务时，Gateway 把停止请求持久化到 SQL，Worker 轮询发现后只取消当前执行任务，不影响它继续接收后续任务。

Worker 异常退出后：

```text
租约停止续期
  -> 租约过期
  -> 其他 Worker 扫描到任务
  -> 原子重领
  -> 从 checkpoint 继续
```

达到 Worker 领取次数上限后，系统会把 Run 和线程标记为失败、结束 SSE，并通过 Outbox 排队发送飞书失败通知，避免页面一直显示“加载中”。

这套远程执行模式并不是多启动一个进程就能成立。它要求 Gateway 和 Worker 使用持久化 SQL、Redis StreamBridge、运行所有权心跳以及共享的 `DEER_FLOW_HOME`。本地单 Gateway、单 Worker 可以使用 SQLite；服务器部署则应使用 PostgreSQL。

因此最终架构可以概括为：

- Gateway 是控制面：接请求、鉴权、调度、SSE、停止、飞书发送。
- Worker 是执行面：运行 Agent、调用工具、截图验收、生成文件。
- Agent 定义保持统一。
- 当前只隔离网站生成 Agent。
- 后续所有长任务 Agent 都可以复用同一套 Worker 协议。

## 小结

回头看，这个 Agent 从想法到落地，其实只做了四件事：

1. 用 Manifest 把“做完”变成可计算的数字——预期截图数 = 页面数 + 业务状态数，验收不再是玄学。
2. 用三层兜底实现无人值守——禁用澄清、强制非交互、自动续跑，把人工介入降到最低。
3. 用飞书推送让等待变得透明——30%、70%、100% 三个里程碑，进度由文件事实驱动。
4. 用架构分离应对长任务——Gateway 管控制与交互，Worker 管执行与恢复，彼此不再共享同一个任务生命周期。

“手搓一个 Agent”并不是手写一个神奇 Prompt。真正的工作，是把一个模糊目标逐步拆解为模型可以创造的部分、代码必须兜底的部分、用户能够观察的状态，以及系统可以严格判断的完成条件。

模型负责创作，系统负责验收、调度和恢复。对长任务 Agent 来说，后半句往往比前半句更决定它能不能真正投入使用。
