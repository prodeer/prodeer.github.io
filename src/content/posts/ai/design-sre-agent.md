今天看到一篇关于 [SREAgent 完成新一轮融资](https://mp.weixin.qq.com/s/4AcyVNy5eyS1Op_8L4Zplg?scene=1)的文章。文章提到了告警分析、根因定位、工单处理、主动巡检、Skill 扩展，以及“L4”级别的智能运维服务。这些产品能力让我开始思考一个更具体的问题：**如果让我从零设计一个 SRE Agent，我会怎么设计？**

我不会先从“选哪个大模型”开始，也不会先讨论要不要使用 Multi-Agent。我会先回答三个问题：

- 它在企业运维体系中扮演什么角色？
- 它凭什么对生产环境做出判断？
- 我们又凭什么允许它操作生产系统？

这三个问题，分别决定了 SRE Agent 的系统边界、技术架构和自治上限。

<!--more-->

## 1. 我想设计的不是“AI 运维助手”

先说结论：**我会把 SRE Agent 设计成企业运维体系之上的智能控制面，而不是一个能够调用运维工具的聊天机器人。**

今天的企业通常已经有监控平台、日志平台、Trace 系统、CMDB、发布平台、工单系统和自动化运维平台。问题并不是完全没有数据或工具，而是这些系统彼此割裂：监控知道“哪里异常”，CMDB 知道“它是谁”，发布平台知道“刚刚改了什么”，日志和 Trace 记录“请求经历了什么”，但仍然需要工程师把这些信息临时拼接起来，形成判断，再去不同平台执行操作。

SRE Agent 不应该重建这些系统。它应该站在它们之上，理解当前任务，组织所需上下文，调用已有能力，并对整个处理过程负责。

我会把运维体系分成三层：

![SRE Agent 的系统位置](/images/ai/sre-agent/sre-agent-three-layer-positioning.png)

数据层说明系统发生了什么，能力层提供查询和变更手段，SRE Agent 所在的智能控制层则决定当前应该做什么、是否允许做。它的核心价值不是替代下方的数据和工具，而是让已有系统形成一条能够持续推进、验证结果的工作闭环。

这个定位也排除了几种看起来像 SRE Agent、实际上离生产可用还有很远的形态：

- 给运维知识库套一个聊天界面，只能算运维问答；
- 让模型总结一组告警，只能算事件摘要；
- 把 Shell、SQL、kubectl 直接暴露给模型，是自然语言操作终端；
- 只根据一段日志输出唯一根因，是缺少验证的概率性猜测；
- 在演示环境里自动重启服务，不代表具备生产自治能力。

它们可以是 SRE Agent 的局部能力，但任何一项都不能单独构成完整的 SRE Agent。

## 2. 设计 SRE Agent 的五条原则

明确系统定位后，我会用五条原则约束后续设计：

- **证据优先于结论**：每个判断都要能回到指标、日志、Trace、变更或拓扑关系；
- **编排优先于生成**：核心产物是持续更新的任务状态和行动计划，而不是一段分析文字；
- **确定性系统包围概率模型**：模型表达意图，系统负责校验和执行；
- **自治范围由风险决定**：是否自动执行取决于可逆性、影响面和验证能力，而不是模型有多自信；
- **所有能力必须可评估**：诊断、建议和执行都要能够回放、对照和度量。

其中最重要的分工是：

```text
模型负责：理解、假设、规划、选择
系统负责：校验、授权、执行、记录、验证
```

例如，模型可以提出“回滚 payment-service”，但回滚哪个版本、影响多少实例、由谁审批以及如何验证，必须由确定性系统决定。

## 3. 总体架构：一个智能控制面，六个核心模块

基于上面的定位和原则，我会把系统拆成六个模块：
- Task Gateway 统一告警、IM、工单和巡检任务；
- Context Engine 构造现场；
- Reasoning & Planning 管理假设和调查计划；
- Agent Runtime 管理长任务的状态、预算、中断与恢复；
- Skill Platform 封装运维能力；
- Policy、Execution & Evaluation 负责授权、执行、验证和回放。

![SRE Agent 总体架构](/images/ai/sre-agent/sre-agent-system-architecture.png)

LLM 只存在于 Reasoning & Planning 的一部分。一次故障分析可能持续几十分钟，还要等待查询、审批或系统恢复，因此它本质上是一个可暂停、可恢复的长任务，而不是一次模型调用或 HTTP 请求。

## 4. 三个场景，检验这套设计能否落地

架构图只能说明模块如何组织，不能证明它能够解决真实问题。可以用三个常见场景检验前面的设计：

| 场景 | Agent 首先创造的价值 | 可以逐步开放的能力 |
|---|---|---|
| 发布后错误率升高 | 关联发布时间、错误日志、关键指标、Trace 和影响范围 | 生成回滚方案，满足策略后审批回滚 |
| 无状态服务容量不足 | 对比流量、资源水位、副本数量和容量趋势 | 给出扩容建议，或在限定范围内自动扩容 |
| 下游依赖持续超时 | 沿调用拓扑确认故障边界，排除自身变更和资源问题 | 建议限流、降级、流量切换或升级人工 |

这些场景中，Agent 最先替代的都不是最终决策，而是跨平台的信息收集、关联和初步排查。判断它是否有价值，就看它能否把零散数据变成可行动的证据，而不只是生成一段看起来合理的解释。

## 5. Context Engine：比 Prompt 更重要的基础设施

如果只能优先建设一个模块，我会选择 Context Engine，而不是继续调整 System Prompt。运维判断高度依赖服务拓扑、时间窗口和变更信息；脱离现场，同一条错误日志可能得到完全不同的解释。

我会把上下文分为四类：

| 上下文类型 | 典型数据 | 主要特征 |
|---|---|---|
| 资源上下文 | 服务、集群、实例、Owner、运行环境 | 相对稳定，但必须有明确归属 |
| 关系上下文 | 服务依赖、调用拓扑、部署关系 | 会变化，需要时间版本 |
| 运行上下文 | 指标、日志、Trace、告警、当前容量 | 实时性强，必须绑定时间窗口 |
| 变更与经验上下文 | 发布、配置变更、历史事故、Runbook | 需要来源、审核状态和有效期 |

这四类数据共同组成面向任务的 `Incident Context`。它不一定需要图数据库，但必须保留告警、实例、版本、依赖、变更和历史事件之间的关系。

![SRE Agent 运维上下文图](/images/ai/sre-agent/sre-agent-context-graph.png)

Context Engine 还要处理三个问题：数据是否仍然有效，事实能否追溯到来源，以及哪些信息值得进入有限的上下文窗口。关键事实应携带采集时间、来源和查询参数，海量原始数据则先按服务、时间和异常程度筛选。

因此，好的上下文不是“越多越好”，而是**与当前任务相关、时间一致、来源明确，并且可以继续向下钻取**。

## 6. 推理过程：从“给出答案”改为“管理假设”

真实故障往往有多个可能原因，因此 Agent 不应该从一段日志直接跳到唯一根因，而要维护一份结构化的调查状态：

```text
已确认事实：当前已经被证据支持的信息
候选假设：可能原因及当前置信度
支持证据：哪些数据支持某个假设
反对证据：哪些数据与某个假设冲突
已排除项：为什么排除
待执行动作：下一步查询或验证
停止原因：结论充分、预算耗尽或需要人工介入
```

这里保存的是可审核的决策记录，不是模型冗长的自由思考。Runtime 围绕它循环执行“构造上下文、生成假设、调用 Skill、获取观察、更新假设”，并在证据充分、风险超权或预算耗尽时停止。

一个可靠的 Agent 不只是知道如何继续，也要知道什么时候不应该继续。

## 7. Skill：不是 API 的集合，而是安全的运维能力

把所有平台 API 直接注册成工具，会迅速带来语义不一致和权限失控。我会按照运维意图，而不是底层系统来设计 Skill：

- **Observe**：查询指标、日志、Trace、拓扑、变更和资源状态；
- **Analyze**：异常检测、时间相关性分析、变更影响分析、容量预测；
- **Change**：扩缩容、回滚、限流、流量切换、配置变更；
- **Verify**：验证 SLO、错误率、实例健康和业务检查结果。

一个生产级 Skill 至少需要声明：

| 契约 | 需要回答的问题 |
|---|---|
| 接口契约 | 输入输出是什么，调用前需要满足哪些条件 |
| 权限与风险 | 以谁的身份操作，属于哪一级风险 |
| 影响范围 | 最多影响多少服务、实例或流量 |
| 执行语义 | 是否幂等，如何超时、重试和并发控制 |
| 预演与回滚 | 如何评估影响，失败后如何恢复 |
| 验证规则 | 如何判断动作真正成功 |

例如，“重启工作负载”不能只是包装 Kubernetes API。它还应检查副本数、PDB 和当前流量，限制最大不可用实例数，分批执行，并用错误率和延迟验证结果。

![Skill 受控执行生命周期](/images/ai/sre-agent/sre-agent-skill-lifecycle.png)

Skill 不是“模型可以调用的函数”，而是包含安全语义和完成标准的运维能力。

## 8. 安全与自治：决定它有没有资格进入生产环境

SRE Agent 与普通知识 Agent 最大的差异，是它可能改变真实生产环境。安全治理必须是独立于模型的控制平面，而不是 System Prompt 里的几条提醒：

- 观察类和变更类 Skill 使用不同身份、凭证和执行通道；
- 授权同时绑定环境、服务、动作、任务来源和影响范围；
- 审批必须说明行动依据、风险、影响、回滚和验证方法；
- 实例数、并发数、流量比例和持续时间都要有硬限制；
- 日志、工单和 IM 消息一律视为外部数据，不能改变系统指令或权限。

系统还需要全局停止开关、速率限制、审计和运行回放。真正的安全来自系统约束，而不是期待模型永远做出正确选择。

原文提到了 L4，但自治不应该是整个产品的统一标签，而应绑定具体场景、Skill、服务和环境。

![SRE Agent 自治等级与风险边界](/images/ai/sre-agent/sre-agent-autonomy-risk-matrix.png)

L0 到 L2 分别覆盖知识检索、信息聚合和只读诊断；L3 是人工批准后的执行；L4 则只用于低风险、可验证、可回滚的局部闭环。同一个扩容 Skill，可以在测试环境达到 L4，在核心交易集群里仍停留在 L2 或 L3。**自治不是模型能力排行榜，而是一份风险授权清单。**

记忆同样需要保持克制。

**记忆不等于把每次事故塞回知识库。** Run Ledger 记录运行事实，经过结果验证和人工复盘后，才能提炼为带来源、版本和失效条件的 Case Knowledge。所谓自学习，应该是从可验证记录中提炼候选经验，再经过治理后生效。

## 9. 如何评估和逐步落地

### 9.1 评估体系

SRE Agent 的评估不能只看回答是否流畅，也不能只看最终根因是否命中。一个偶然猜中根因、但调查过程不可复现的 Agent，无法获得生产环境的信任。

我会从四个维度建立评估体系：

| 维度 | 典型指标 |
|---|---|
| 信息处理 | 告警压缩率、关键上下文召回率、事件摘要准确率 |
| 诊断质量 | 根因 Top-K 命中率、证据完整度、错误假设排除率 |
| 行动质量 | 建议采纳率、执行成功率、验证通过率、回滚率 |
| 安全与效率 | 越权拦截率、错误动作率、MTTA、MTTR、人工介入次数和单任务成本 |

尤其不能只优化 MTTR：一个快速但错误的操作，可能让故障更快扩大。上线也应遵循相同逻辑，从历史回放和影子模式开始，先开放只读能力，再逐步走向审批执行和有限自治。

### 9.2 要不要使用 Multi-Agent

设计 SRE Agent 时，很容易按照组织分工拆出告警 Agent、日志 Agent、网络 Agent、数据库 Agent 和执行 Agent。但角色更多，并不代表系统更可靠。Agent 之间还会增加上下文同步、状态一致性、任务分派和结果合并的成本。

我的第一版会采用：

```text
一个主控 Agent + 一组专业 Skill + 一个确定性执行与治理系统
```

只有出现下面几类真实需求时，我才会拆分多个 Agent：

- 不同领域需要完全不同的模型、Prompt 和上下文；
- 多条调查路径确实需要并行推进；
- 敏感信息或操作权限需要强隔离；
- 单个上下文已经无法承载完整任务；
- 每个角色都有可以独立评估的目标和产物。

即使引入 Multi-Agent，执行生产变更的也不应该是一个自由规划的“执行 Agent”，而应是受策略控制的确定性执行服务。**组织里有多少团队，不代表系统里就需要多少 Agent。**

### 9.3 落地路线

架构可以设计得很完整，但第一版不应该试图同时解决所有运维问题。我的落地顺序不会从自动修复开始，而是先把运维数据变成可用上下文，再逐步建立诊断、执行和自治能力。

![SRE Agent 五阶段落地路线](/images/ai/sre-agent/sre-agent-implementation-roadmap.png)

这条路线的关键不是能力越多越好，而是每前进一个阶段，都用可观察、可评估的结果换取更高权限。第一阶段的价值不是自动修复，而是自动完成信息收集、关联和初步排查。

## 10. 小结

> 我会把 SRE Agent 设计成企业运维体系之上的智能控制面，而不是一个能执行命令的聊天机器人。
>
> 它通过 Context Engine 构造现场，管理候选假设和证据，再用受控 Skill 推动调查和行动。模型负责理解、规划和选择，确定性系统负责校验、授权、执行、记录与验证。
>
> 落地时先做只读的信息收集和辅助诊断，再开放人工审批执行，最后只在低风险、可验证、可回滚的场景中实现有限自治。

大模型决定了 SRE Agent 能想到什么，工程系统决定了它能不能进入生产环境。一个好的 SRE Agent，不是敢于操作生产，而是知道自己什么时候还没有资格行动。
